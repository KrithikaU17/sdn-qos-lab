================================================================================
  UDP QoS — Simple Guide (qos_udp.py + Mininet)
================================================================================

WHAT IS THIS?
-------------
This is a small teaching program that shows how Quality of Service (QoS)
works when many types of network traffic share one slow "bottleneck."

It does NOT need real routers or SDN hardware. Everything runs on your PC
using UDP (a simple "send and forget" network protocol).

Think of it like a busy checkout line at a store:
  - Many customers (packets) arrive from three lanes: voice, video, bulk.
  - The cashier can only serve a fixed number of customers per second (capacity).
  - If too many people wait, some are turned away (packet drops).
  - A "manager" (the controller) can change rules: "serve voice customers first."

================================================================================
THE THREE TRAFFIC TYPES
================================================================================

  voice  — Small, steady traffic (like a phone call). Should stay smooth.
  video  — Medium traffic (like streaming). Important but can buffer a bit.
  bulk   — Heavy traffic (like file downloads). OK to slow down when busy.

In the program, each packet is labeled with one of these names so the server
knows which queue to use.

================================================================================
MAIN PIECES OF THE PROGRAM
================================================================================

1) CLIENT (traffic generator)
   - Sends UDP packets to the server at a rate you choose (packets per second).
   - Each packet carries: a label (voice/video/bulk), a number, and a timestamp.

2) SERVER (congested receiver)
   - Receives packets and puts them in THREE separate waiting lines (queues).
   - A scheduler takes packets out one at a time, but only as fast as
     "capacity" allows (e.g. 800 packets per second).
   - If a queue is full, new packets for that class are dropped.

3) CONTROLLER (like SDN policy)
   - Sends a small JSON message over UDP to change:
       * weights  — who gets served more often when all queues have work
       * capacity — how fast the bottleneck can process packets
   - During the lab you change SDN weights mid-test to favor voice.

4) REPORTER
   - Every second, prints stats: speed, delay, loss, and a "fairness" number.

================================================================================
HOW PACKETS LOOK (SIMPLIFIED)
================================================================================

Each UDP message starts with a short header, then padding to reach the size
you want (default 512 bytes):

  [ magic "QOS1" ] [ class id ] [ sequence ] [ send time ] [ padding... ]

The server checks the magic and class id. Bad packets are ignored.

================================================================================
SCHEDULING — WHO GOES NEXT?
================================================================================

When several queues have packets waiting, the server does weighted scheduling:

  - Each class has a "weight" (e.g. voice=8, video=3, bulk=1).
  - Higher weight → that class gets more turns at the bottleneck.
  - This is a simplified idea similar to Weighted Fair Queuing (WFQ).

Default server weights favor voice. The Mininet lab can start equal (1:1:1),
then sdn-controller switches to 8:3:1 so you can see voice improve under congestion.

================================================================================
WHAT THE NUMBERS MEAN (SERVER OUTPUT)
================================================================================

Each second you may see lines like:

  time class  throughput_kbps latency_ms loss_% processed queued

  throughput_kbps — How much data that class got through in the last second
                    (kilobits per second).

  latency_ms      — Average time packets waited (milliseconds). Higher =
                    more congestion or lower priority.

  loss_%          — Percent of offered packets dropped (queue full or never
                    served in time). High loss = overload.

  processed       — Total packets this class has successfully "served" so far.

  queued          — How many packets are still waiting in that class's queue.

  Jain fairness index — How equal the throughputs were among classes in that
                    second (1.0 = perfectly equal). Prioritizing voice
                    usually lowers fairness but helps voice.

================================================================================
WHY CONGESTION HAPPENS IN THE MININET LAB
================================================================================

Example client rates (packets per second):
  voice  300
  video  500
  bulk   700
  Total offered ≈ 1500 pps

Default server capacity: 800 pps

So the server cannot keep up → queues fill → drops → loss_% goes up.
Changing weights shifts who suffers most when everyone is competing.

================================================================================
HOW TO RUN (WINDOWS)
================================================================================

You need Python 3. Open PowerShell in the folder that contains qos_udp.py.

--- MININET (course lab — see README.md) ---

  Terminal 1: ryu-manager ryu_qos_controller.py
  Terminal 2: sudo python3 mininet_qos.py
  Mininet CLI: start clients on h1, h2, h3; hsrv tail -f /tmp/qos_srv.log
  Terminal 3: python3 qos_udp.py sdn-controller --weights voice=8,video=3,bulk=1

--- Standalone socket test (optional, not Mininet) ---

Terminal 1 — start the server:

  python qos_udp.py server --capacity 800 --weights voice=8,video=3,bulk=1

Terminal 2 — send traffic (run three commands in separate windows, or one
after another):

  python qos_udp.py client --class voice --rate 300 --duration 30
  python qos_udp.py client --class video --rate 500 --duration 30
  python qos_udp.py client --class bulk  --rate 700 --duration 30

Terminal 3 — change policy while traffic is running:

  python qos_udp.py controller --weights voice=8,video=3,bulk=1
  python qos_udp.py controller --weights voice=1,video=1,bulk=1 --capacity 500

--- HELP ---

  python qos_udp.py -h
  python qos_udp.py server -h
  python qos_udp.py client -h

If "python" is not found, try:  py -3 qos_udp.py -h

================================================================================
DEFAULT PORTS
================================================================================

  Data (clients → server):       UDP 19000  (--port)
  Control (controller → server): UDP 19001  (--control-port)

Default host: 127.0.0.1 (your own machine only).

================================================================================
PROGRAM MODES (SUMMARY)
================================================================================

  server      Run receiver, queues, scheduler, control socket, live stats.
  client      Send one traffic class at a given rate for a duration.
  controller  Send one policy update (weights and optional capacity).

================================================================================
CODE STRUCTURE (qos_udp.py)
================================================================================

  CLASSES / NAMES     — Maps voice, video, bulk to numeric IDs in packets.
  QoSServer           — Main server: receive, schedule, control, report threads.
  send_traffic()      — Client loop: rate-limited UDP sends with timestamps.
  update_policy()     — Controller: JSON command and response over UDP.
  main()              — Parses CLI and runs the chosen mode.

================================================================================
REAL-WORLD CONNECTION (CONCEPT ONLY)
================================================================================

Real networks use similar ideas:

  - Classification — mark traffic (DSCP, VLAN, app type).
  - Queues — separate buffers per class at routers/switches.
  - Scheduling — WFQ, strict priority for voice, etc.
  - Control — SDN controllers or management systems change policy without
    rewiring every device.

This script compresses that into one Python process for learning.
